# Mac Setup: Building the iOS App

How to build and install the MusicSync iOS app from a clean Mac. The Mac is only used
for iOS builds and signing; day-to-day development happens on Windows.

Facts below (tool versions, menu paths, Apple free-account limits) were checked against
Expo SDK 57 docs, the Expo SDK 57 changelog, Apple's Xcode system requirements, and
Expo's environment-setup guide as of August 2026. Anything not fully confirmed is
marked `[verify]`.

## Background: how this repo builds for iOS

- npm-workspaces monorepo: `shared/`, `server/`, `app/`. Always `npm install` at the
  **repo root**, never inside `app/`.
- The app uses Expo SDK 57 (React Native 0.86) with Continuous Native Generation:
  `app/ios/` is **gitignored** and generated by `npx expo prebuild`. Never hand-edit
  files under `app/ios/` expecting them to survive - they are wiped by the next clean
  prebuild. Native configuration lives in `app/app.config.ts`.
- Two variants, selected by the `APP_VARIANT` env var read in `app/app.config.ts`:
  - `APP_VARIANT=dev` -> "MusicSync (Dev)", bundle id `com.jiaqi.musicsync.dev`,
    a dev client that loads JS from Metro.
  - unset -> "MusicSync", bundle id `com.jiaqi.musicsync`, a standalone Release
    build with the JS bundle embedded (no Metro needed to run it).
  The generated `app/ios/` holds **one variant at a time**; switching variants means
  re-running prebuild with the right env var.
- Native pieces that get compiled: `react-native-track-player`,
  `@kesha-antonov/react-native-background-downloader`, the Expo SDK modules, and the
  local Expo module in `app/modules/backup-exclusion` (autolinked as a pod).
  `react-native-track-player` 4.1.2 is a legacy NativeModule, but React Native 0.86
  keeps the TurboModule interop layer used to load it on iOS. After every React
  Native or track-player upgrade, run the physical-device playback gate in
  [`PLAYBACK-SMOKE-TEST.md`](PLAYBACK-SMOKE-TEST.md).
- Signing uses a **free Apple ID** (Personal Team). Consequences: provisioning
  profiles expire after 7 days (weekly re-install, see section 4), at most 10 new
  App IDs per rolling 7 days, and at most 3 free-provisioned apps installed on the
  device at once.

## 1. One-time Mac preparation

Requirements (Expo SDK 57): Xcode 26.4+, Node.js 22.13+. Xcode 26.4 itself requires
**macOS Tahoe 26.2 or later** - update macOS first via System Settings > General >
Software Update if needed. Watchman is not needed (only SDK 55 and earlier required it).

1. **Install Xcode** from the Mac App Store (search "Xcode", Install). It is a
   ~10 GB+ download; start it early. If the App Store copy fails to install, download
   from https://developer.apple.com/xcode/ instead.
2. **Launch Xcode once.** Accept the license and let it install additional components
   when prompted.
3. **Install the Command Line Tools:** Xcode > Settings... (Cmd+,) > Locations >
   set the "Command Line Tools" dropdown to the installed Xcode version.
   (Alternatively `xcode-select --install` in Terminal.) This also provides `git`.
4. **Install the iOS Simulator runtime** (needed for section 2): Xcode > Settings... >
   Components > under "Platform Support" next to iOS, click Get/Install.
5. **Install Homebrew** (Terminal):

   ```sh
   /bin/bash -c "$(curl -fsSL https://raw.githubusercontent.com/Homebrew/install/HEAD/install.sh)"
   ```

   Follow the "Next steps" it prints to add `brew` to your PATH.
6. **Install Node and CocoaPods:**

   ```sh
   brew install node cocoapods
   node --version   # must be >= 22.13
   pod --version
   ```

   Expo SDK 57 still uses CocoaPods for iOS native dependencies (verified against the
   SDK 57 changelog - no Swift Package Manager migration yet). `npx expo run:ios`
   runs `pod install` for you automatically, but the `pod` tool itself must exist.
   If you prefer an LTS-pinned Node, use `nvm` instead of brew's `node`.
7. **Clone and install:**

   ```sh
   git clone <repo-url> ~/Project
   cd ~/Project
   npm install        # repo ROOT - installs all workspaces incl. app/ and shared/
   ```

## 2. First Simulator run (no signing needed)

Simulator builds are unsigned, so this verifies the whole native toolchain without
touching Apple accounts. Good for UI work later, too.

```sh
cd ~/Project/app
npx expo prebuild -p ios --clean   # generates app/ios/ from app.config.ts
npx expo run:ios                   # pod install + xcodebuild + boots a Simulator
```

Notes:

- Since SDK 57, `expo prebuild` clears and regenerates `ios/` **by default**;
  `--clean` is now just explicit. Use `--no-clean` only if you know why.
- The first build compiles all pods and can take 10-20 minutes. Later builds are
  incremental and much faster.
- `run:ios` without flags builds Debug for the Simulator and starts Metro; the app
  loads JS from Metro. Press Ctrl+C to stop Metro when done.
- No `APP_VARIANT` was set, so this is the release-variant app identity
  (`com.jiaqi.musicsync`) in a Debug build - fine for a toolchain smoke test.

## 3. First install on the iPhone (Release variant)

### 3a. Prepare the phone

1. Connect the iPhone to the Mac with a USB cable. Unlock it and tap **Trust** when
   asked to trust the computer.
2. Enable Developer Mode: on the iPhone, Settings > Privacy & Security > scroll to
   **Developer Mode** > toggle on > the phone restarts > after unlocking, confirm
   **Turn On** and enter your passcode. (The Developer Mode row only appears once a
   Mac with Xcode has talked to the phone - do step 1 first.)

### 3b. Add your Apple ID to Xcode

1. Xcode > Settings... > **Accounts** > click **+** > "Apple ID" (or "Apple Account")
   > sign in with your free Apple ID (expect a two-factor prompt on your Apple
   devices).
2. The account appears with a team named **"Your Name (Personal Team)"**, role User.
   That is the free-tier team you will sign with.

### 3c. First build attempt and the signing dance

```sh
cd ~/Project/app
npx expo run:ios --device --configuration Release
```

- `--device` with no argument shows an interactive picker; select your iPhone
  (you can also pass a name: `--device "Jiaqi's iPhone"`).
- `--configuration Release` embeds the JS bundle, so the installed app runs
  standalone with no Metro.

The very first device build **will fail on signing** ("Signing for 'MusicSync'
requires a development team") because the freshly generated Xcode project has no team
selected. Recent Expo CLI can also prompt for the team itself and, on real devices,
uses `ios.appleTeamId` from the app config; because this project uses a dynamic
`app.config.ts`, the CLI cannot write the value back automatically. Fix it in Xcode:

1. Open the generated workspace:

   ```sh
   open ios/MusicSync.xcworkspace
   ```

   (or `xed ios`; the exact `.xcworkspace` name matches the app name in
   `app.config.ts`).
2. In the left navigator select the top **MusicSync** project entry, then the
   **MusicSync** target under "Targets", then the **Signing & Capabilities** tab.
3. Check **Automatically manage signing** and set **Team** to
   "Your Name (Personal Team)". Xcode registers the bundle id and creates a 7-day
   provisioning profile.
4. If Xcode flags signing errors on any *other* target (Pods resource bundles or the
   local `BackupExclusion` module can surface this in some Xcode versions
   `[verify]` - often they need no signing at all), select that target's Signing &
   Capabilities tab and pick the same Personal Team.
5. Close Xcode and re-run:

   ```sh
   npx expo run:ios --device --configuration Release
   ```

   (Building with Xcode's Run button also works, but the CLI keeps the Expo-managed
   flow in one place.)

Optional but recommended: note the 10-character Team ID (visible in Signing &
Capabilities after picking the team) and add `appleTeamId: 'XXXXXXXXXX'` to the `ios`
block of `app/app.config.ts`. Then every future clean prebuild regenerates the
project with the team already set, and the Xcode dance above never recurs.

### 3d. Trust the developer certificate on the phone

The install succeeds but launching shows **"Untrusted Developer"**. On the iPhone:

1. Settings > **General** > **VPN & Device Management** (on much older iOS:
   "Profiles & Device Management").
2. Under "Developer App", tap **Apple Development: your@appleid.email**.
3. Tap **Trust "Apple Development: ..."** and confirm. On recent iOS the confirm
   button may read **Allow & Restart** and reboot the phone `[verify - wording seen
   for enterprise apps on iOS 18+; personal-team apps have historically been plain
   "Trust"]`.
4. Launch MusicSync from the home screen.

Before treating the device build as complete, run
[`PLAYBACK-SMOKE-TEST.md`](PLAYBACK-SMOKE-TEST.md). It verifies local and streamed
playback, background audio, queue operations, interruptions, and Lock Screen/Control
Center commands on the physical iPhone.

First launch on the LAN: iOS will ask for **Local Network** permission (the app
declares `NSLocalNetworkUsageDescription`, and plain-HTTP LAN traffic is allowed via
`NSAllowsLocalNetworking`). Tap Allow, or the phone cannot reach the desktop music
server. If you mis-tapped: Settings > Privacy & Security > Local Network > MusicSync.

## 4. The weekly re-sign ritual (free Apple ID)

Free-tier provisioning profiles expire **7 days** after they are created. When the
profile lapses, the installed app stops launching (it bounces back to the home
screen, or iOS shows an "app is no longer available" style alert). The app itself and
its data are still on the phone - it just needs a fresh install signed with a fresh
profile. (The Settings screen's "built N days ago" nudge, driven by `extra.buildDate`
in `app.config.ts`, exists to remind you before this happens.)

Once a week, on the Mac, with the iPhone plugged in (and unlocked):

```sh
cd ~/Project
git pull
npm install          # cheap no-op unless dependencies changed
cd app
npx expo run:ios --device --configuration Release
```

- With automatic signing, Xcode/Expo mint a new 7-day profile during the build - no
  manual Xcode steps, as long as `app/ios/` still has the team set (or you added
  `appleTeamId`, see 3c). A clean prebuild without `appleTeamId` re-triggers the
  Xcode signing dance.
- **App data survives.** The bundle id `com.jiaqi.musicsync` is stable, so iOS treats
  the install as an app update: the SQLite library database and all downloaded music
  in the app container are preserved. Data would only be lost if you deleted the app
  or changed the bundle identifier.

## 5. Dev-client workflow for active UI development

For iterating on UI you do not want a full native rebuild per change. Build the dev
client **once**, then only JS changes flow in over Wi-Fi from Metro - which can run
on the Windows machine.

One-time (or after native deps / config change), on the Mac:

```sh
cd ~/Project/app
APP_VARIANT=dev npx expo prebuild -p ios --clean
APP_VARIANT=dev npx expo run:ios --device
```

Notes:

- `APP_VARIANT=dev` must be set for **both** commands so the generated project and
  the build both use `com.jiaqi.musicsync.dev`. This is a second App ID on the free
  account (2 of your 3-apps-per-device budget) and installs alongside the release
  app. It goes through the same signing/trust steps as section 3 the first time,
  and it also expires every 7 days.
- This overwrites `app/ios/` with the dev variant. To build the release variant
  again later, prebuild again **without** `APP_VARIANT`:
  `npx expo prebuild -p ios --clean` (then section 4's command).
- For Simulator-based UI work, the same but without `--device`:
  `APP_VARIANT=dev npx expo run:ios` (no signing needed).

Daily loop - Metro can run on the Windows machine, same Wi-Fi as the phone:

```powershell
cd C:\Users\jiaqi\Documents\Project\app
npx expo start --dev-client --lan
```

Open "MusicSync (Dev)" on the iPhone; the dev launcher lists development servers
found on the LAN, or scan the QR code from the terminal with the iPhone Camera, or
type the URL manually (`http://<windows-ip>:8081`). Fast Refresh then applies JS
edits live. If the phone cannot see the server, allow Node.js through the Windows
firewall on Private networks (port 8081) and make sure phone and PC are on the same
subnet.

The dev client only needs rebuilding (on the Mac) when native things change: adding
or upgrading a library with native code, editing `app.config.ts` native config, or
changing `app/modules/backup-exclusion` - and, on the free account, weekly anyway.

## 6. Troubleshooting

**`pod install` fails / CocoaPods errors.**
Make sure `pod --version` works (`brew install cocoapods`). For repo/spec errors, from
`app/ios/` run `pod repo update` then `pod install`. Nuclear option (safe - the whole
directory is generated): delete `app/ios/` and re-run
`npx expo prebuild -p ios --clean` (with `APP_VARIANT=dev` if building the dev
variant). Also try `npx expo install --fix` from `app/` to correct mismatched
Expo-package versions after a `git pull`.

**"Failed to register bundle identifier."**
Someone else's Apple account already owns that bundle id, or automatic registration
failed. Change the identifier in `app/app.config.ts` (e.g. append a suffix:
`com.jiaqi2.musicsync` for both variants), prebuild `--clean`, rebuild. Warning: a
new bundle id is a new app on the phone - downloaded music and the library database
do not carry over.

**"Your maximum App ID limit has been reached."**
Free accounts may create at most **10 App IDs per rolling 7 days**. Each new bundle
id you register (each variant counts) consumes one. There is no override - wait out
the window, and stop churning bundle-id suffixes.

**Signing error: "requires a development team" after a working setup.**
A clean prebuild regenerated `app/ios/` and dropped the team selection. Redo section
3c, or permanently add `appleTeamId` to `app.config.ts`.

**Device not detected by `run:ios --device`.**
Use a data-capable USB cable; unlock the phone; accept the "Trust This Computer"
prompt; confirm Developer Mode is on (Settings > Privacy & Security > Developer
Mode). Check Xcode sees it under Window > Devices and Simulators - if it is stuck
"preparing" or needs a "Connect via network" toggle, let Xcode finish first. A
locked phone at install time is the most common cause of last-step failures.

**Build succeeds, app installs, launch bounces back to home screen.**
Either the certificate is not yet trusted (section 3d) or the 7-day profile expired
(section 4). Both fixes take under a minute.

**App runs but cannot reach the music server.**
1. Local Network permission: Settings > Privacy & Security > Local Network >
   MusicSync must be on (iOS only asks once).
2. The server speaks plain HTTP on the LAN; the app config already opts in via
   `NSAllowsLocalNetworking`, which covers cleartext to local hosts. If you ever
   point the app at a non-local HTTP URL, iOS App Transport Security will block it -
   that needs a different ATS exception, not a server-side fix.
3. Same Wi-Fi network / subnet for phone and desktop; check the Windows firewall
   allows the server's port for Private networks.
4. Simulator note: the Simulator shares the Mac's network, so the server must be
   reachable from the Mac.

**Xcode version rejected ("requires Xcode 26.4 or later").**
Expo SDK 57 needs Xcode 26.4+, which needs macOS 26.2+. Update macOS, then Xcode,
then re-select Command Line Tools in Xcode > Settings > Locations.
